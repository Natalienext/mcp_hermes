# Гриль: модуль памяти для Hermes (ДЗ Л7–Л8)

- **Дата:** 2026-10-15
- **Постановка:** `клод_агенты/ДЗ - 6.docx` (задание 1), проект Л6 — `wardrobe-api`, `wardrobe-mcp` (сводка `клод_агенты/ДЗ-Л6-сводка.md`), пример — `клод_агенты/example-memory` (Go). Наш код — Java / Spring Boot.
- **Фича:** агент-стилист в Hermes помнит устойчивые сведения о своём единственном пользователе (предпочтения, ограничения, сведения о себе) и получает похожие факты во вход на каждом сообщении через хук, без вызова tools.

## Решения

1. **Один пользователь, поле `user_id` есть.** У факта и хода хранится `user_id`, значение одно, берётся из env (`me`). Гардероб Л6 остаётся без пользователя. — Агент — личный помощник одного человека, но поле даёт коду проверку «чужой факт» и готовность к gateway без миграции.
2. **Три рода фактов: `preference`, `constraint`, `background`.** `decision` не вводим. — В гардеробе решение работает как ограничение или предпочтение; лишний род заставляет экстрактор гадать, а `constraint` отдельно нужен, чтобы модель превращала его в исключения `wardrobe_search`.
3. **Тему (scope) придумывает модель:** короткий ключ латиницей через дефис (`skirts`, `color-blue`, `height`); экстрактор видит кандидатов с их темами; код проверяет формат ключа и правило «на теме одна действующая запись». — Закрытый список тем слишком крупный: «не ношу юбки» и «не ношу шорты» легли бы на одну тему и заменяли бы друг друга.
4. **В память не идёт переменное:** вещи гардероба («у меня есть красная юбка» — они в таблице `item`), разовые просьбы («сегодня без юбки»), погода, планы на день, настроение («сегодня грустно, хочу в чёрном»). Граница: «у меня есть юбка» — нет, «я не ношу юбки» — да. **Это правило держит только промпт экстрактора** (для отчёта: инвариант, который держит промпт). — Вещи уже лежат в базе гардероба, а переменное завтра неправда.
5. **Вывод модели (`inferred`) записывается, но в recall не идёт.** Виден в `memory_list` с пометкой; не может заменить факт `stated`. — Агент не отвечает на догадках, а в базе видно, что модель додумывает; сказанное не перетирается выводом.
6. **«Забудь» — только про факты памяти, по id.** Стираются текст и цитата у факта и всех его прежних версий (цепочка замен) и текст сообщения пользователя в исходных ходах. След остаётся: id, род, тема, даты записи и забывания, статус `forgotten`, сессия, где попросили забыть. Вещи гардероба не трогаются (в `wardrobe-api` удаления нет). Забыть по теме или «всё про юбки» разом нельзя. — След требует инвариант ДЗ; он сохраняет цепочку замен целой, объясняет, почему агент «перестал знать», и держит правило «запись только добавляется»; тема в следе показывает, что она освободилась.
7. **Отдельный Maven-модуль `wardrobe-memory`** в том же репозитории: свой процесс, свой порт (например 8091), своя база; слои с теми же именами, что в Л6 (`domain/`, `application/`, `infrastructure/`, `web/`). Код Л6 не трогаем. — Прогон «до» останавливает сервис памяти и не должен выключать `wardrobe_search`; в отчёте — одна строка об этом отходе от буквы ДЗ («модуль сервиса Л6»).
8. **База памяти — SQLite + FTS5, файл.** — Факты переживают перезапуск; снимок для замера — копия файла; прямое сравнение с примером. (`wardrobe-api` держит H2 in-memory — для памяти не подходит.)
9. **Хук — отдельный модуль `wardrobe-memory-hook` без Spring** (JDK `HttpClient` + Jackson, fat jar); HTTP-таймаут к сервису короткий (≈1–2 с), меньше таймаута Hermes; хук только читает stdin, ходит в сервис и печатает `{"context": …}`, все проверки — в сервисе. — Хук стартует новым процессом дважды за ход; Spring Boot добавил бы 2–3 с к каждому ответу.
10. **MCP-tools памяти — отдельный модуль `wardrobe-memory-mcp`** (Spring AI, `@McpTool`, stdio, адрес сервиса из env, логи в файл); tools `memory_remember`, `memory_forget`, `memory_list`. — Не переписываем `wardrobe-mcp` из Л6; Spring тут не мешает — сервер стартует раз на сессию.
11. **Экстрактор — OpenRouter + `deepseek/deepseek-v4.1-flash`**, всё через env (`EXTRACTOR_BASE_URL`, `EXTRACTOR_MODEL`, `EXTRACTOR_API_KEY`). — Проверено в задании 0 на том же ключе, дёшево, меняется одной переменной.
12. **Экстракция — одна попытка, без повторов.** Недоступен / таймаут / не тот JSON → ход помечается «экстракция не удалась», причина в лог, фактов нет. Плохое отдельное решение отклоняется, соседние записываются. — Для одного пользователя потеря фактов одного хода некритична, повторы и устойчивая очередь сильно усложняют сервис.
13. **Recall:** FTS по тексту факта и цитате среди действующих `stated` фактов пользователя; не больше **N = 5** строк (env, 0 выключает); строка `id | род | возраст | факт | «цитата»` (пример: `f-012 | constraint | вчера | Не носит юбки | «я не ношу юбки»`). — Мало токенов; род подсказывает модели, что `constraint` — жёсткий запрет для `wardrobe_search`.
14. **Только CLI** (`hermes -p l78 chat -q`), обвязку gateway не снимаем. — Сценарии идут через CLI, Telegram не подключён, `user_id` один (Р1).
15. **«Запомни» сверяет цитату с единственным незавершённым ходом пользователя** (от сохранения сообщения в pre до ответа в post). Нет незавершённого хода → отказ с ошибкой для модели. Новый pre при незавершённом старом ходе → старый закрывается как прерванный. Факт, уже записанный через `memory_remember`, экстрактор повторно не пишет (тема занята, кандидат → SKIP). — Сообщение даёт хук, а не модель, поэтому модель не подсунет свои слова.
16. **Сценарии замера — тема юбок** (в гардеробе юбки id 17, 18; запрет виден в вызове `wardrobe_search` как `excludeType=[SKIRT]`):
    - Засев S1 (отдельная сессия): «Я не ношу юбки, мне в них неуютно» → `constraint`, тема `skirts`.
    - **S1 — факт поднимается.** Вход: «Собери мне образ на свидание, можно с юбкой или платьем». Прошёл: в recall id факта, в ответе нет вещей 17 и 18 (или в вызове `excludeType=[SKIRT]`). Не прошёл: агент предложил юбку.
    - Засев S2 (поверх базы S1): «Теперь я иногда ношу юбки, если они миди» → замена, старый факт `superseded`.
    - **S2 — замена.** Тот же вход. Прошёл: recall поднял новый факт, старый «не носит юбки» не назван как текущий.
    - Засев S3 (поверх базы S1): «Забудь, что я не ношу юбки» → `forgotten`.
    - **S3 — «забудь».** Тот же вход. Прошёл: запрета на юбки нет ни в ответе, ни в recall.
    - Мутация: лимит recall 0, вход S1 — обязан не пройти.
    - Входы можно подогнать после research (см. Д3).
17. **Вне рамок** — см. раздел ниже. — Сознательно сужаем итерацию.

## Допущения (проверить)

- **Д1.** Модель не назовёт одну мысль двумя разными темами (иначе на одну мысль две действующие записи). Проверка — сценарий S2.
- **Д2.** В CLI `extra.user_message` приходит чистым текстом пользователя, без служебных добавок Hermes. Проверка — research.
- **Д3.** Неизвестно, находит ли токенайзер FTS5 «юбкой» по «юбки». Проверка — research; при промахе входы сценариев берут ту же словоформу, что в факте.
- **Д4.** Ход, ждущий экстракции во время перезапуска сервиса, не будет разобран (очередь в памяти процесса).

## Вне рамок

1. Несколько пользователей; gateway / Telegram, включая снятие обвязки (`envelope`).
2. Удаление или изменение вещей гардероба через память и «забудь».
3. Повторы экстракции и очередь, переживающая перезапуск.
4. Векторный поиск (Qdrant) и детектор битых записей — бонусы ДЗ.
5. Изменения кода Л6 (`wardrobe-api`, `wardrobe-mcp`).
6. Перевод `constraint` в параметры `wardrobe_search` кодом: это решает модель по строке recall; сервис памяти о гардеробе не знает.

## Критерии приёмки (EARS)

- **AC-1.** ЕСЛИ цитаты решения экстрактора нет в сообщении пользователя, ТО СИСТЕМА ДОЛЖНА отклонить решение с причиной в логе и записать соседние решения.
- **AC-2.** ЕСЛИ цитата есть только в ответе ассистента, ТО СИСТЕМА ДОЛЖНА отклонить решение.
- **AC-3.** ЕСЛИ цитаты `memory_remember` нет в незавершённом ходе, ТО СИСТЕМА ДОЛЖНА вернуть модели ошибку и ничего не записать.
- **AC-4.** ЕСЛИ `memory_remember` вызван без незавершённого хода, ТО СИСТЕМА ДОЛЖНА вернуть ошибку.
- **AC-5.** ЕСЛИ заменяемый факт не существует, не действует или принадлежит другому `user_id`, ТО СИСТЕМА ДОЛЖНА отклонить замену.
- **AC-6.** КОГДА замена принята, СИСТЕМА ДОЛЖНА оставить на теме одну действующую запись: у старой статус `superseded`, новая ссылается на старую.
- **AC-7.** ЕСЛИ новый факт попадает на тему, где уже есть действующая запись, ТО СИСТЕМА ДОЛЖНА отклонить его.
- **AC-8.** ЕСЛИ факт `inferred` заменяет факт `stated`, ТО СИСТЕМА ДОЛЖНА отклонить замену.
- **AC-9.** КОГДА факт `inferred` записан, СИСТЕМА ДОЛЖНА не возвращать его в recall и показывать в `memory_list` с пометкой.
- **AC-10.** КОГДА выполнен `memory_forget` по id, СИСТЕМА ДОЛЖНА стереть текст и цитату факта и его прежних версий и текст сообщения в исходных ходах, поставить статус `forgotten`, записать дату и сессию и больше не возвращать факт в recall.
- **AC-11.** ЕСЛИ `memory_forget` получил id несуществующего или недействующего факта, ТО СИСТЕМА ДОЛЖНА вернуть ошибку.
- **AC-12.** ЕСЛИ тема не в формате ключа, ТО СИСТЕМА ДОЛЖНА отклонить решение.
- **AC-13.** КОГДА пришёл запрос recall, СИСТЕМА ДОЛЖНА вернуть не больше N строк формата `id | род | возраст | факт | «цитата»`, только действующие `stated` факты этого пользователя.
- **AC-14.** КОГДА лимит recall равен 0, СИСТЕМА ДОЛЖНА вернуть пустой ответ тем же кодом, без отдельной ветки.
- **AC-15.** КОГДА пришёл запрос «ход завершён», СИСТЕМА ДОЛЖНА ответить «принято», не дожидаясь экстракции.
- **AC-16.** ЕСЛИ экстрактор недоступен или вернул не тот JSON, ТО СИСТЕМА ДОЛЖНА пометить ход неразобранным, записать причину в лог и не записывать фактов.
- **AC-17.** КОГДА приходит новый pre при незавершённом ходе, СИСТЕМА ДОЛЖНА закрыть старый ход как прерванный.
- **AC-18.** ЕСЛИ сервис памяти недоступен или не ответил в срок, ТО хук ДОЛЖЕН напечатать пусто и выйти с кодом 0 раньше таймаута Hermes.
- **AC-19.** ЕСЛИ на stdin хука некорректный JSON, ТО хук ДОЛЖЕН напечатать пусто и выйти с кодом 0.
- **AC-20.** КОГДА засеян факт S1 и пришёл вход S1, СИСТЕМА ДОЛЖНА вернуть id этого факта в recall.
- **AC-21.** КОГДА сервис запущен с лимитом recall 0, прогон S1 ДОЛЖЕН не пройти (мутация).
- **AC-22.** АГЕНТ ДОЛЖЕН ПРОДОЛЖАТЬ отвечать, а `wardrobe_search` — работать, когда сервис памяти остановлен.
- **AC-23.** СИСТЕМА ДОЛЖНА ПРОДОЛЖАТЬ отвечать на `GET /api/items` как в Л6; код `wardrobe-api` и `wardrobe-mcp` не меняется.
